# Artifact Hub Publishing

Publish rich Markdown or HTML documents to a configured Artifact Hub MCP service, then verify the public/detail page. Use when the user says “Artifact Hub”, “arthub”, “artifact.sharosoo.com”, or asks to register/publish a rich artifact.

## Critical interpretation rule

**Do not assume “Artifact Hub” means a local HTML file, desktop artifact index, or chat attachment.**

When the user refers to `artifact.sharosoo.com`, `arthub`, or an MCP-registered artifact service, the requested deliverable is a server-side publication through the configured MCP server. A local file may be a staging artifact, but it is not completion.

## Same-post consolidation and hard deployment constraints

When the user says “위에 했던 것도 같이”, “같은 게시물로”, or “누락없이”, treat the request as a canonical consolidation task—not as permission to publish a second related artifact. Inventory every already-prepared local draft and the latest correction, then compose one Markdown body before the single publish. Preserve all requested subject areas (including earlier appendices if the user explicitly requires no omissions), but put the latest correction in a prominent top-level conclusion so superseded advice is not mistaken for the final decision. When a deployment constraint is absolute, repeat it in the opening callout, architecture diagram, decision table, and deployment section; do not leave an older alternative framed as recommended. After publication, canonical-read the one artifact and verify distinctive markers for every merged source section plus the corrected constraint.

For the Cloud Run/DBOS case, the final architecture must distinguish **Cloud Run Service as API/submitter only** from **Cloud Run Worker Pool as the DBOS worker target**. Never recommend deploying the DBOS worker to a Cloud Run Service merely because Service has native autoscaling. Explain Worker Pool external scaling (CREMA, Prometheus/queue-depth metrics, or an external control-plane scaler) and the scale-to-zero caveat for an in-pool scheduled scaler. Include DBOS Conductor/Postgres recovery and workflow versioning when discussing Worker Pool rollouts.

## CRDT-first rule for collaborative artifacts

When the requested architecture includes collaborative editing, offline work, shared canvases, Yjs, or CRDTs, treat CRDT support as a first-class content and recovery requirement—not as a WebSocket/provider checkbox. The artifact must explicitly separate:

- Yjs `Y.Doc` and binary updates as the collaborative content/merge model;
- durable artifact metadata, ACL, revision, audit, and snapshot manifests in the owning database;
- large snapshots/updates and attachments in object storage;
- Redis/queues for dispatch, compaction, indexing, and outbox work;
- Centrifugo/WebSocket provider for live binary-update fan-out and ephemeral Awareness only.

Do not use Centrifugo history as CRDT source of truth, and do not mix the artifact CRDT update log with the DBOS execution/run journal. Require state-vector reconciliation after reconnect or realtime-history loss, update-id/hash deduplication, snapshot/compaction coverage, server-side read-only/ACL enforcement, and explicit separation of Awareness (cursor/presence/typing) from durable document content. Agent edits must pass through the same authorized artifact-update port as user edits and retain correlation/causation links to the agent run. See `references/crdt-collaborative-artifact.md` for the contract, recovery flow, authoritative references, and test matrix.

## Custom runtime architecture rule

When the user is evaluating Pydantic AI for an existing agent platform, treat Pydantic AI as **reference material only** unless the user explicitly asks for a runtime integration. Do not introduce a Pydantic AI compatibility engine, adapter, or parity implementation by default. Extract useful ideas—typed dependencies and outputs, capability/toolset modeling, stream events, deferred tools, cancellation, history repair, and evaluation hooks—and implement the required contracts in the user's custom runtime. Keep provider requests, prompt-cache topology, usage normalization, pricing, billing settlement, durability, CRDT mutation, and replay under the user's own ports and code.

Preserve the user's canonical product and service names. Do not invent generic provisional names for a product the user has already named, such as replacing `gpai-v2` with a generic collaboration service name. Use `gpai-v2` for the bounded context/project and derive process-specific entrypoints such as `gpai-v2-api`, `gpai-v2-orchestrator`, and named workload pools only when the deployment design calls for them. Do not fall back to a generic `gpai-v2-worker` after API/orchestrator/executor/projection process types have been mapped. Before publishing, search the complete body for stale provisional names and remove them rather than explaining the old names in the final document.

For a full architecture consolidation, do not stop at a component diagram. Include one canonical project structure, each module's implementation additions and ownership, ports/adapters and forbidden imports, data/persistence and event contracts, retry/idempotency/authorization/observability, deployment target and entrypoint, migration order, and quality gates. When the design includes an agent runtime, explicitly cover multi-user conversations: participant and actor attribution, conversation ordering, private versus shared context, concurrent-run policy, and visibility scopes. Explicitly cover steering as a durable control-plane signal rather than ordinary chat text: typed signals, role-aware authorization and priority, signal sequence/cursor, safe step-boundary application, requested-versus-confirmed cancellation, pause/resume checkpoints, idempotency, audit outcomes, and deterministic conflict policy. Treat CRDT artifact edits and steering signals as separate ordering authorities.

## Workflow

1. **Identify the target from the direct source.**
   - If the user provides an Artifact Hub URL, inspect that site first.
   - Confirm a configured MCP server named `arthub` (or the relevant server) and discover its tools.
   - Prefer the native MCP tools named like `mcp__arthub__publish_artifact`.
2. **Search before creating.**
   - Call `list_artifacts` with a distinctive title/query and an appropriate limit.
   - If an equivalent document exists, read it before deciding whether to update it.
3. **Choose format deliberately — 정혁 standing preference (2026-08-30): Markdown body + wrapped blocks, never full-page HTML for an article.**
   - Publish articles as `format: md` by default. The whole document is Markdown: prose, code, exact-value tables, citations, and fallback explanations stay in Markdown.
   - Before reaching for any live block or HTML, check what Markdown natively supports in the body: headings/paragraphs/lists/blockquotes/tables/links/images/footnotes/task lists, GitHub callouts (`> [!NOTE]` `> [!TIP]` `> [!WARNING]` `> [!CAUTION]` `> [!IMPORTANT]`), code fences with language + `title=` meta and `// [!code ++]` `// [!code --]` `// [!code highlight]` `// [!code focus]` markers, ` ```mermaid ` diagrams, the native ` ```chart ` preset (column, bar, line, area, pie, radial, polar, radar), `:::` layout components (`grid`, `card`, `stat`, `compare`, `timeline`, `figure`, `details`). Quote every mermaid node, decision, and edge label in md bodies — `A["한글 라벨"]`, `B{"질문"}`, `-- "예" -->` — and use `state "한글 이름" as id` in stateDiagram-v2; quoted Korean labels with em dashes and punctuation render reliably, while unquoted labels containing parentheses break the parser. Keep each label on one line; do not use `<br>` breaks. Most "I need HTML" cases are one of these.
   - Wrap only complex blocks — components Markdown, `:::` components, or the `chart` preset cannot express (custom interactive diagrams, bespoke visualizations) — in self-contained ` ```html render ` fences inside the same md body. This is the default shape; do not wait for the user to request it.
   - `format: html` (whole document) only when the deliverable is genuinely a full-page interactive experience (dashboard, prototype, slide) and the user asked for that. A normal article must not become a full-HTML post. Publishing a prose-heavy HTML document now triggers an `article-as-html` warn from the server.
   - Use the native fenced `chart` preset for data visualization. Artifact Hub converts it to inline semantic Charts.css markup; do not hand-write Charts.css tables inside `html render`. (Chart types: column, bar, line, area, pie, radial, polar, radar.)
   - Raw HTML directly in the Markdown body is invalid (`no-raw-html` lint error); rich content goes through fenced live blocks.
4. **Freeze the canonical body, then publish with stable metadata.**
   - For a Git-backed document corpus, finish local structural/security/terminology validation and run `git diff --check` **before** the remote mutation. Compute the canonical body hash only after that check. Publish those exact bytes and do not normalize whitespace or headings afterward; any post-publish byte change invalidates exact-read-back claims and requires a new artifact version plus refreshed version/hash records.
   - Set an explicit title and deterministic slug for a new artifact.
   - For a revision, copy the exact existing `(project, slug)` from `read_artifact`; an ID, title, or detail URL does not target the update by itself, and inventing a cleaner slug creates a duplicate.
   - Set project, tags, visibility, format, and `agent_source` when available.
   - Preserve the returned `slug`, document ID, version, raw link, and detail link. If an intended update returns `Created v1` instead of an incremented version, treat it as a duplicate-creation alarm and stop.
5. **Verify the result from the service.**
   - Open the returned Artifact Hub detail URL.
   - Confirm title, tags, version, visibility, preview, and the document’s actual rendered content.
   - For HTML, ensure the iframe preview loads and interactive controls appear.
   - For md bodies the detail page shows metadata only (title, version, tags, visibility, an Open action) with the body absent from the DOM — do the pixel-level check on the raw content URL in a browser: every image `complete === true` and `naturalWidth > 0`, mermaid SVG count equals the mermaid fence count in the body, and the opening blockquote text is present.
6. **Report completion with the correct link for the user.**
   - For 정혁’s workflows, return the published raw-content URL beginning with `artifact-content.sharosoo.com` as the primary link **when it has been independently verified to serve the expected revision**. If raw verification is stale, inaccessible, or returns an auth/scope error, use the verified detail-page URL instead and state that raw delivery was not independently verified.
   - Briefly state version, visibility, and what the artifact contains.
   - Keep Discord responses to a short progress/result summary plus that raw-content link. Put the long technical body in Artifact Hub rather than repeating it in chat.
   - When the article embeds images, attach 1–3 key figures to the Discord reply as `MEDIA:/absolute/path` lines.

## Publishing cron and generated reports

- Publish the clean deliverable, not the execution envelope. Remove stored prompts, scheduler headers, tool-planning chatter, calculation-module notes, implementation paths, automatic-scoring caveats, and other production metadata unless provenance is specifically useful to the reader. A reader-facing article should feel like one finished document, not a report explaining how the agent made it.
- Treat image-sourcing policy as production metadata too. Do not add reader-facing sections such as “we only used Wikimedia Commons” or narrate rejected image sources. Keep only the minimum per-image author/license attribution required for reuse; the article body should stay about its subject.
- When the user asks for a polished Korean artifact, run a dedicated natural-Korean review before publishing. Rewrite English-shaped word order, generic nouns such as `기능`/`영역`/`해석 틀`, repeated `현대적으로`, and mechanical sentence endings in context rather than relying on string substitution. Keep traditional or technical terms, but explain them in ordinary Korean and add Korean readings when the audience may not read the original script.
- Prefer a canonical report file produced by the job over reconstructing content from its delivery transcript. When only a cron output file exists, extract the final response body; chained jobs may contain several `## Response` sections, so select the last response section and then the intended top-level heading.
- Keep Markdown as the default. Use standalone HTML only for genuinely interactive or custom-UI artifacts.
- Sanitize imported GitHub/PR excerpts before publishing. Truncated PR descriptions commonly leak raw `<!-- ...` template comments and angle-bracket placeholders such as `<issue number>`, which Artifact Hub rejects under `no-raw-html`. Remove leaked comment fragments and escape literal placeholders, then republish. For cron-generated GitHub-derived bodies (depth-mode daily report, industry weekly, etc.), run `scripts/sanitize_github_markdown.py` first — it strips multi-line HTML comments, escaped `&lt;details&gt;`/`&lt;summary&gt;` leftovers, the standard `<issue number>` / `<name>` / `<model>` / `<repo>` / `<branch>` / `<title>` / `<author>` / `<org>` / `<scope>` placeholders, and any other bare `<[A-Za-z][^>]*>` tags outside fenced code blocks, and returns a non-zero exit code under `--strict` if anything is left.
- Search for the exact title before creating each dated report. Use deterministic dated slugs so retries do not create ambiguous duplicates.
- After publication, verify both the detail-page metadata and the opened rendered document. Checking only the raw endpoint is insufficient. In cron/CDN environments, append `?v=<published-version>` (or another cache-busting query) to the detail and raw URLs when the plain detail URL shows an older version — the value must be an EXISTING version number (a nonexistent version 404s and a non-numeric one 400s, and either error page then poisons later browser checks); for latest use the plain URL; then confirm the detail page says `Open vN`, shows current tags/visibility, and the opened document H1/body matches the canonical `read_artifact` revision. Treat a cache-stale plain URL as a verification caveat, not as evidence that the publication failed.
- For generated reports, run a focused post-publish probe that checks local structure, Discord character limits/section markers, canonical body length, rendered raw phrases, detail-page version/tags, and absence of literal `**`/raw HTML. Create that probe through an OS-safe temporary file with a `hermes-verify-` prefix, run it, and delete it; report it as ad-hoc verification rather than claiming the project test suite is green.

## Project classification and reclassification

When a user separates reviewed documents (`blog`) from unfinished drafts (`blog-draft`), treat project classification as part of the deliverable rather than an index-only change.

**Sequential deepen scope (정혁 — hard gate):** A mixed index that lists both projects does **not** authorize rewriting drafts. On “이어서 / 순차적으로 / 남은 거 / 다음꺼”, default to **`project=blog` only**. Leave `blog-draft` untouched unless the user explicitly asks to flesh drafts.

**Mandatory preflight before every deepen batch (do not skip):**
1. `list_artifacts(project="blog", limit=100)` → this ID set is the **only** rewrite allow-list.
2. If the user pastes a keep-list / search result / index excerpt, intersect that title set with the `blog` list. Do **not** open IDs that only appear under Architecture / Product / ML / “draft에 있을거야” sections.
3. Apply recency filter when stated or previously established (정혁 default: skip pieces modified within the last ~5 hours; prefer still-early `v1`/`v2` stale rows).
4. Never call `update_artifact` with `project="blog-draft"` during a blog deepen run. Never “continue into drafts” because the mixed index numbers them next.
5. If an index still links IDs whose live `project` is `blog-draft`, treat that as index drift: stop deepening those rows; clean the index so only live `blog` IDs remain in reviewed sections.
6. If `blog` contains IDs outside the keep-list the user just defined, **do not deepen them** — move to `blog-draft` via `move_artifact` or archive/delete only when the user asked to clean orphans.

Bare index order and compaction “next draft ID” hints must not override project/recency/keep-list gates. Details: `references/iterative-blog-draft-series.md` → Project scope gate.

1. Inventory the current project and explicitly identify reviewed artifacts, draft artifacts, the index, and unrelated documents.
2. For every reclassified document, read the canonical body and current version before mutation.
3. Submit the complete body to `update_artifact` with the destination project and exact original slug. A project change creates a new artifact ID/version; capture it immediately.
4. Read back the new ID/version and verify body, slug, and project before moving to the next document.
5. Update every index link from the old ID to the new ID.
6. Archive the old source artifact only after the destination copy and index link are verified. Permanent deletion may require a separate `artifact:delete` scope; if unavailable, report the old copy as archived, not deleted.
7. Re-list both projects and confirm reviewed documents are active in `blog`, drafts are active in `blog-draft`, and old source copies are not active in the original project.

Do not claim a move is complete when only the index link changed or when the old source remains active in the original project.

## Updating an existing artifact

1. Search/list and identify the document.
2. Call `read_artifact` to fetch the latest published body and version.
3. Resolve the exact document ID from the persisted publish result or `list_artifacts`, confirm it with `read_artifact`, then call `get_draft`. If a human has an unpublished draft, do not overwrite it silently. If `get_draft` returns `Document not found`, treat that as an ID/lookup mismatch and recover the exact ID; do not misclassify the error as an unpublished-draft conflict.
4. Use `update_artifact` with `base_version` for optimistic concurrency when the format is unchanged **and metadata must not change**.
5. After `update_artifact`, immediately read back the returned version with `read_artifact` before starting the next item. Verify the returned body, version, slug, and project—not merely the update acknowledgment. For exact-content batch syncs, compare the read-back body to the local source file (including title and Markdown structure), not just metadata. Some deployments prepend generated metadata lines such as `# Title (vN, md)` and `slug=... project=...` to the canonical read-back; strip only that known prefix before comparing the body, and require the remaining content to match exactly. If the update returns a version conflict, read the latest version and report the conflict; never overwrite a human or newer revision with `force` unless the user explicitly authorizes it.
5a. For long architecture consolidations, keep one local canonical Markdown body and append new class-level sections to that body before one in-process update; do not create a second “related” artifact. Large pseudocode/YAML snippets must be fenced. If the linter reports `prefer-table` against a line inside an imported architecture draft, inspect whether an unfenced code block or colon-bearing phase heading caused the detector; fence the block or replace the heading colon with an em dash, then update sequentially until `warnings: []`.
6. After the per-item read-back, re-list the artifact and verify tags/visibility. Some Artifact Hub deployments clear tags when the update operation cannot carry metadata. If metadata was cleared, call `publish_artifact` with the same `(project, slug)` and explicit `title`, `tags`, `format`, `visibility`, and `agent_source`; confirm it appends a version to the same artifact ID. For verification, query by the exact title or a distinctive body phrase; some deployments do not match a slug-only `q` search even when the slug is present.
6. To change format (for example, standalone HTML → Markdown), call `publish_artifact` with the existing `(project, slug)` and the new `format`; confirm it appended a version to the same artifact ID.
7. Use `force` only with explicit user authorization after warning about the draft/conflict.
8. Re-open the detail page and the rendered/raw document, then verify the new version, format, tags, visibility, and content.

## Deleting test, duplicate, or preflight documents

When the user explicitly asks to remove server-side test artifacts, first search with `list_artifacts` and identify the complete target set by exact title, slug, project, and document ID. Do not delete similarly named production documents. The configured live MCP surface currently exposes seven document operations: `publish_artifact`, `update_artifact`, `move_artifact`, `get_draft`, `list_artifacts`, `read_artifact`, and `delete_artifact`. `move_artifact` changes project/optional slug without resubmitting the body or creating a version. `delete_artifact` is available for archived documents but requires a delete-capable personal token; browser OAuth is intentionally read/write-only for MCP clients. If a particular client exposes only the first six tools, use the authenticated REST archive/delete fallback below after verifying the live routes.

1. Archive each target with `POST /api/artifacts/:id/archive`.
2. Permanently delete it with `DELETE /api/artifacts/:id` and JSON body `{"confirmation":"<exact slug>","expected_version":<current version>}`.
3. Require both responses to succeed and record `deletedVersions` plus `storageCleanupComplete`.
4. Verify with `list_artifacts` searches for every target title/tag/slug. A missing result is the completion criterion.

**Critical pitfall:** `DELETE /api/artifacts/:id/archive` restores/unarchives a document (`archived: false`); it does not permanently delete it. Permanent deletion requires the archive-then-delete sequence above. If a target was accidentally unarchived, re-archive it before issuing the permanent delete request. See `references/deletion-and-archive.md` for the route behavior and verification recipe.

## External-reader technical series workflow

When the user asks for a multi-part engineering series about an internal implementation:

1. Draft the complete series narrative first. Do not block drafting on literature research; use papers, benchmarks, and vendor documentation later as search/validation material.
2. Generalize the published narrative for readers who do not know the product, repository, team, or internal tool names. Internal code identifiers belong only in private evidence notes unless they are independently public.
3. A public model name such as Morph may appear in the article when its role is explained. Separate the model's public/vendor-reported claims from evidence that the architecture is better for the user's specific editor.
4. Keep editor-specific evaluation design in a separate appendix artifact. The main article may state the hypothesis and the missing validation, but should not present the evaluation protocol as if it were production evidence.
5. Publish sequentially: publish one part, perform canonical `read_artifact` read-back, audit the opening, terminology, audience assumptions, and claim boundaries, then use that tone for the next part. Do not bulk-publish an unreviewed series. Match H1 to index as `N. Title` (not `Part N —`).
6. After each update, verify version, body, tags, visibility, and warnings. If an update clears metadata, publish the exact same `(project, slug)` again with explicit title/tags/format/visibility and verify the appended version.
7. Treat Artifact Hub warnings as unresolved editorial work. Add prose before tables or subsections when the linter reports `empty-section`, convert dense key/value bullets to tables when it reports `prefer-table`, and continue until the final revision has no warnings.
8. Report work mode honestly (hygiene / editorial / evidence deepen). Editorial template passes are not “살 붙임”.

## Batch draft-series workflow

When publishing many related drafts such as blog topics, research briefs, or a document series:

1. Create a persistent Markdown checklist before publishing. Include one row per deterministic slug plus batch-level checks for duplicate search, publish, metadata verification, and rendered-content verification.
2. Prefer problem-revealing titles over implementation labels when the user is choosing blog directions. Each rough technical draft should begin with six one-line fields: material, problem definition, alternatives, trade-off, conclusion, and strength to emphasize.
3. Search every title/slug before any creation. For a multi-document revision, resolve and validate every target identity first: use `list_artifacts` by exact slug/title, then `read_artifact` and `get_draft` for each document before the first mutation. Do not trust a supplied document ID without read-back confirmation; if an ID returns `Document not found`, stop that item and recover the canonical `(id, project, slug, version)` from `list_artifacts` rather than guessing or proceeding with a substitute. Load the live update schema and validate one real target. Update sequentially, immediately reading the returned version after every successful update, and record each version/raw link into the checklist before moving on. Keep each topic number stable across the filename, manifest, checklist, and index even when the index groups entries by domain. For reader-facing editorial rewrites, audit one artifact's opening, internal vocabulary, chronology, and audience assumptions before publishing the next; do not bulk-edit the series and defer the audience review to the final index pass. A batch is complete only when every requested item has a verified update or an explicitly reported unresolved identity/conflict; do not end mid-batch merely because some items succeeded.
4. Keep going until every row is published and verified; do not stop after generating local Markdown or publishing only an index.
5. Publish a separate index artifact after the individual documents are complete. Group links by topic and state that it is an index, not an extra draft in the requested count. Track reader-ready documents and selection-oriented rough drafts as separate progress counts; never make `26/26 complete` imply that rough candidates are polished articles.
6. Verify the full batch from three views: `list_artifacts` for project/tags/version, `read_artifact` for the latest source, and detail/raw URLs for metadata and rendered structure. Visually inspect at least one representative document after programmatic checks.
7. Treat canonical MCP read-back as the publication source of truth when the raw endpoint is stale, CDN-cached, inaccessible, or returns an authentication/scope error. Do not declare the publish failed solely because raw HTTP verification failed: confirm the artifact ID, slug, version, title, and body through `read_artifact` and `list_artifacts`, then use the detail-page URL in the index or user-facing link if it is the stable accessible route. Keep the raw URL only when it has been independently verified to serve the expected revision.
8. If a broad source draft is decomposed into a multi-article series, keep the source artifact unless deletion is explicitly requested, omit it from the numbered reader-facing index, and state that it has been superseded. Do not count both the superseded source and every replacement article in the collection total.
9. Treat rough-draft publication and evidence-backed concretization as separate phases. If the user asks to deepen the series, add a second `0/N` progress section instead of marking the whole project complete merely because every placeholder was published.
8. Include both user-specified topics and useful topics the agent discovered during research. Do not silently narrow the batch back to only the items repeated in the user's latest message; show the complete inventory in the index.
9. Deepen one artifact at a time as a new version: check for a human draft, preserve metadata, add chronology/code/tests/alternatives/claim boundaries, verify the rendered version, and then update the index to `1/N`, `2/N`, and so on. Keep the next item explicit so the sequence is resumable.
10. If the user says to avoid live blocks, use plain Markdown headings, paragraphs, lists, tables, blockquotes, and code fences only. Do not add `html render` or chart fences merely to make a draft look richer.

See `references/iterative-blog-draft-series.md` for the two-phase rough-draft → evidence-backed-version workflow, project scope gate, title numbering, hygiene/editorial/evidence modes, and progress-index pattern. See `references/gpai-blog-evidence-map.md` when evidence-deepening 정혁’s GPAI runtime/context/durable `blog` keep-list against the monorepo. See `references/canonical-read-vs-raw-verification.md` when MCP canonical read-back disagrees with raw HTTP/CDN verification or when a broad source artifact is replaced by a numbered series.

## Cloudflare deployment and OAuth recovery

When the user asks to redeploy Artifact Hub or its Sharosoo auth provider, verify the Artifact Hub requested scopes against the auth provider's per-client D1 allowlist before deploying. Apply the idempotent auth client seed, use `pnpm run deploy` (not bare `pnpm deploy`), run Artifact Hub's full test suite, and verify both live OAuth redirect behavior and authenticated MCP access. A Wrangler exit code of 1 from `/workers/routes` can mean the Worker upload succeeded but the token lacks `Workers Routes:Edit`; confirm the new 100%-traffic deployment and live endpoints before reporting the outcome. ## Reader-first restructuring of transcript and lecture artifacts

When a user asks to make an existing transcript, translation, or lecture artifact “better organized,” treat it as a reader-facing editorial revision, not as another transcript dump.

1. Preserve the existing `(project, slug)` and update the same artifact after `read_artifact` and `get_draft`; do not create a duplicate merely because the title or H1 changes.
2. Lead with a thesis or one-paragraph orientation, then present metadata, a conclusion-first summary, the conceptual model, detailed source-derived sections, practical implications, claim boundaries, and takeaways.
3. Convert chronological timestamps into a logical structure when the source is a talk. Keep timestamps as anchors inside a detailed appendix or source section rather than making them the primary navigation.
4. Preserve a source appendix when the existing artifact promises a full translation or original transcript. Label the reorganized Korean prose as a structured synthesis so readers can distinguish it from verbatim source text. **Exception (정혁 2026-08-10):** when the user explicitly says the result must be 하나의 완전한 문서 / 전사본이면 안 됨 / 영어 원문 전사도 필요없음, drop the transcript and English-original appendix wholesale, strip production metadata (caption provider, segment counts, "재구성한 정리본입니다" notes), and deliver one standalone article. Enrich it with official vendor references for the concepts the talk mentions: `curl -sSL -o` the linked PDF, extract text with `import pymupdf` (the `fitz` alias is deprecated; `file` reporting "0 page(s)" on a valid PDF is a false alarm — trust pymupdf's page count), read the extracted text, fold concrete claims (token budgets, structure rules, test areas) into the body, and close with a `## 참고자료` list.
5. Explicitly separate speaker claims from curator synthesis. Treat numerical cutoffs, architecture recommendations, and causal explanations from a short talk as heuristics unless the source provides measurements or experiments.
6. For `empty-section` warnings, add one natural introductory sentence immediately under an H2 before a table, list, or first H3. Iterate one warning source at a time, then re-read the canonical body and confirm `warnings: []` before final verification.
7. Verify the same artifact ID, slug, project, version, and body through `read_artifact`; then inspect the cache-busted raw URL and detail page. A successful update must be reported as a version increment, not merely as a successful tool acknowledgment.

## Rich technical brief checklist

A strong architecture artifact should usually include:

- Clear thesis and maturity/status badge
- Architecture diagram with ownership and durability boundaries
- Component or backend comparison
- Data/control-flow walkthrough
- Storage/schema or protocol internals where relevant
- Trade-offs, performance caveats, and production warnings
- Decision guide (“use X when…”) rather than only descriptive prose
- Primary source links
- Responsive layout and readable semantics
- For 정혁's Korean research/comparison articles ("조사해서 정리해서 올려줘" / "비교해서 정리"), the established house structure is: H1 title + one-paragraph intro framing the question, a `> **한눈에 보는 결론**` blockquote with the verdict up front, a small meta table (조사 시점 / 주요 1차 자료 / 비교 기준), numbered sections with `[n]` inline citations, and a closing `## Sources` numbered link list mapping every `[n]`. Formal 합니다체, comparison tables where the subject is a comparison, and claim boundaries ("공식 단일 답변은 없으므로 자료 종합 추론" style caveats) where sources are partial. Project `default` with a descriptive English slug. Follow this shape for future research artifacts so the collection stays consistent. When the article's premise is reactions/reviews for items a seller or vendor lists, treat each seller's product description as marketing copy, not evidence — run per-item web searches for community threads (갤러리·클리앙·퀘존·아크라·루리웹 등) and cite those, keeping seller copy to a one-line comparison anchor at most.
- For guide-type artifacts (게임·도구 플레이 설명서), 정혁's shape. **Open ELI12-first**: a one-sentence goal statement, the ≤3 rules that differ from the genre the reader already knows, then real gameplay stills in chronological order with one-line captions — before any dense section. A guide whose opening dives straight into component terminology gets rejected as too hard; when the user asks for ELI12, source the stills from a real play video (see `references/ai-diagram-and-photo-annotation.md` → How-to video frame stills) rather than restating the same text more simply. Then: separate 구성요소 (components) and 룰 (rules) sections, a value-calculation section that turns the component/economy rules into tables the reader can compute with, and an interactive `html render` hands-on simulator (a playable turn or walkthrough following the real logic) placed BEFORE the strategy/mental-model sections. State simplifications (1v1 slice, example card numbers) inside the simulator intro paragraph, never as a footnote. Verify the arithmetic for every published table with a quick script before publishing.

## Pitfalls

- **Wrong target:** creating `/home/.../artifact.html` and claiming it is in Artifact Hub.
- **Skipping duplicate search:** publishing a second document when an existing slug should be versioned.
- **Unverified publish:** trusting the MCP response without opening the returned detail page.
- **Wrong share link for the user:** choose the link convention from the user/profile. For 정혁, return the `artifact-content.sharosoo.com/raw/<id>` URL as the primary link only when it has been independently verified to serve the expected revision; otherwise return the verified `artifact.sharosoo.com/a/<id>` detail page and state the raw verification gap. Do not silently substitute one for the other.
- **Draft overwrite:** updating without checking for a web-edited unpublished draft.
- **Marketing overclaim:** omitting preview/experimental status or turning roadmap goals into current guarantees.
- **Raw HTML in Markdown:** placing `<div>`/`<table>` directly in the Markdown body instead of a fenced `html render` block.
- **`no-raw-html` also fires on generic type arguments inside inline code.** `` `PagedKV<layout, page_bits>` `` and `` `store_row<layout, vec>` `` were rejected as raw HTML even though they sit in backticks — the linter matches `<[A-Za-z][^>]*>` anywhere outside fences. Rewrite as prose (“layout과 page_bits를 template 인자로 받는 `PagedKV`”) instead of fighting it.
- **Tooling arity/return-shape traps when publishing from a cron script.** `scripts/sanitize_github_markdown.py` takes positional input AND output (`--strict in.md out.md`); a single path exits 2. The in-process `read_artifact` handler returns a JSON *string* (`{"result": "# Title (vN, md)\nslug=… project=…\n\n<body>"}`), so `json.loads` it before reading `result`, strip the generated prefix plus one blank line, and only then byte-compare with the local body. For raw-URL checks use `curl -o /dev/null -w '%{http_code} %{size_download}'` — the same URL through `subprocess.run(..., capture_output=True, text=True)` reported ~89KB where curl reported 121KB for the identical revision, which would look like a truncated body.
- **Label tokens that carry a colon** (`op: moe`, `ci: full pre-merge approved`) should be written `op-moe` / `ci full pre-merge approved` in adjacent bullets, per the `prefer-table` pitfall above.
- **Fragile emphasis boundaries:** some Artifact Hub Markdown renders emphasis literally instead of as bold when it wraps Korean quotation marks, spans an inline-code node, or contains parenthesized values immediately followed by a Korean particle. Examples observed: `**《제목》**`, `**“문구”**`, an emphasis span around backticks, `**$20.6B(55%)**로`, `**학습 가능한 가중(α)**`, `**2.5×**로`, `**GDN(Gated DeltaNet)**`. Put punctuation and parentheses outside the delimiters—`《**제목**》`, `**GDN** (Gated DeltaNet)`, `**학습 가능한 가중** (α)`, “약 2.5배라고”—never wrap one emphasis span around backticks, and prefer dropping bold on long phrases over fighting the renderer. **Do not insert raw `<strong>`** — `no-raw-html` rejects the body. After opening the rendered document, inspect the DOM for `<strong>` and search visible text for stray `**`; if any are present, rewrite the sentence rather than retrying the same delimiter pattern. Refined triggers observed 2026-08-09: a bold span that STARTS with a quote — `**"못 쓴다"가 아니라 ...**` — leaves literal `**` in rendered text, while quotes in the middle of a bold span (`**... "사용자 → IP"를 ...**`) render fine; a bold span containing a parenthesized value directly followed by a Korean particle (`**Synapse는 Python(Twisted)**으로`) also breaks. Same-line inconsistency observed 2026-08-09: `**실시간 전송 계층(PUB/SUB 서버)**이고` leaked literal `**` while its sibling `**채팅 프로토콜 전체(…)를 구현한 분산 표준**이다` on the same line rendered fine — the renderer is not deterministic per pattern, so move parens/quotes outside the delimiters preemptively in every bold span (or drop bold on long phrases), never wait for the rendered check to find the one that broke. Fast verification recipe on the raw endpoint: `curl -sS --compressed <raw-url> -o /tmp/check.html` then `grep -o '\*\*' /tmp/check.html | wc -l` — 0 is clean, 2 = one broken span, 4 = two; **always pass `--compressed`** — without it curl stores gzip bytes and byte-level greps report phantom `\*\*` matches (observed 2026-09-15: grep counted 2 in gzip bytes, 0 after decompression; file(1) still says 'HTML document' because gzip headers precede it, so trust the count anomaly, not file(1)); locate each with `grep -o '.\{40\}\*\*.\{40\}' /tmp/check.html`. Run these as simple single-purpose commands — multi-pattern one-liners mixing Korean text and quoted patterns can trip the terminal command guard and get hardline-blocked.
- **Setext-heading trap after patching markdown near a `---` separator.** If a patch (or chunked write) removes the blank line between a paragraph and a `---`, the paragraph becomes an H2 underline and the document structure silently breaks. After any edit near `---`, verify with `nl -ba` that a blank line precedes the separator and re-insert it if swallowed. Observed 2026-08-09: a patch consumed the blank line before `---`; the missing line was caught during the linter-fix pass, not by the linter. The same trap fires when `---` follows a table row (`| 리소스 | ... |\n---`) and it surfaces as a **phantom `empty-section` warning whose line number points at the text line, not the rule** — deleting the nearby offending H3 heading does NOT clear it (observed on the Matrix-vs-Centrifugo doc: warning persisted across two revisions until the blank line was restored). Preflight before any publish: `grep -B1 '^---$' body.md` — every preceding line must be blank; check both paragraph-before-rule and table-row-before-rule cases. If an `empty-section` warning survives a heading-removal fix at the same line, suspect the setext trap before touching content.
- **Chunked-write `cat` join swallows the blank line before H2 headings.** After `cat p1.md p2.md p3.md > final.md`, a chunk ending with a single `\n` glues the next chunk's first `## Heading` to the previous paragraph (`...다.\n## ...`); canonical `read_artifact` shows the missing blank line. Normalize after joining: `awk '{ if ($0 ~ /^## / && prev != "") print ""; print; prev=$0 }' final.md > tmp && mv tmp final.md`, and preflight with `awk 'prev ~ /[가-힣a-zA-Z0-9]$/ && $0 ~ /^## / {print NR": "prev" -> "$0}' final.md` (empty output = clean). Same "blank line swallowed" family as the `---` setext trap, different manifestation. Observed 2026-08-10 on a 3-chunk Korean article: v7 read-back showed `가능하다.\n## 내 harness…`; the awk pass fixed all heading boundaries and v8 verified clean.
- **Inline code inside task-list items:** Artifact Hub can visually duplicate checkbox text and expose literal backticks when a `- [ ]` or `- [x]` item contains inline-code spans. This may look correct in the semantic DOM while being visibly broken. Keep task-list text plain; put code-formatted hashes, paths, and slugs in a neighboring normal bullet or table. Re-open the raw rendered document and visually inspect the checklist after publishing.
- **Charts in live HTML:** loading Charts.css from a CDN or hand-writing chart tables inside an iframe. Use the native `chart` fence so charts remain static, accessible, searchable, and printable.
- **Visual verification skipped:** checking only DOM counts or publish status without confirming that labels, values, bars, images, and long categories are visible and unclipped. For Charts.css bar charts, inspect the rendered light-theme chart: `valueLabels: outside` can place pale labels on a pale background. Prefer `valueLabels: inside` when it yields reliable contrast, keep an adjacent exact-value table, and verify zero-value labels separately because they have no bar behind them. For external images, confirm actual pixels are visible—not merely an `image` node or alt text. A screenshot or direct visual inspection—not semantic DOM text alone—is the completion test.
- **Full-page PDF as “figure”:** whole-page `pdftoppm` embeds rejected by user. Crop caption + drawing/image region, trim margins, upload with `sharosoo-cdn put` (`cdn.sharosoo.com`), place inline under the claim. See `references/pdf-figure-crop-and-host.md`.
- **Figure gallery-only:** paper figures dumped at the end without narrative anchors — each crop goes under the paragraph that uses it.
- **Fragile external image redirects:** Markdown embeds that use redirect endpoints such as Wikimedia Commons `Special:Redirect/file/...` may appear as broken images under throttling/CORS even when the source page works. Prefer direct `upload.wikimedia.org` original or supported-size thumbnail URLs, retain a separate file-description/license link, and re-check the full rendered page. See `references/external-image-verification.md`.
- **Image hosts that reject `HEAD`:** A source CDN may return `405 Method Not Allowed` for `HEAD` even though the image is healthy. Do not classify that response as a broken image. Retry with a small ranged `GET` (for example `Range: bytes=0-31`), verify a successful image response and the expected file signature, then perform the decisive check in the published Artifact Hub document: every rendered image must have `complete === true` and non-zero `naturalWidth`/`naturalHeight`. For translated figures, keep a localized caption and a separate full-size source link.
- **Deepening the wrong project:** following a mixed blog index into `blog-draft` after the user scoped `blog` only. **Always** `list_artifacts(project=blog)` first; rewrite only those IDs. Never pass `project=blog-draft` on update during a blog deepen run.
- **Index ≠ live project:** an index row can still link a draft ID after reclassification. Trust live `project` from `list_artifacts`/`read_artifact`, not the index section alone. Clean the index if reviewed sections still link draft IDs.
- **Keep-list vs full mixed index:** when the user pastes only Runtime / Context / Durable (or “이것들만”), do not deepen Architecture/Product/ML rows even if the full index still numbers them.
- **Editorial reported as deepen:** failure opening + tables + `Design lesson` / clone `Discarded alternatives` / series-wide `Generalization beyond…` without chronology, code contracts, or session-run tests is **editorial**, not flesh. When asked how flesh was added, answer with hygiene vs editorial vs evidence-deepen and A/B/C tiers — never a single “deepened” line. Details: `references/iterative-blog-draft-series.md` → Three work modes.
- **Part N titles after numbered index:** keep-list H1 must be `N. Title` matching the index; `Part 1 —` is wrong once the collection is renumbered 1…N.
- **MCP bridge fallback:** if deferred `tool_call` cannot invoke arthub tools, use the in-process registry handler (`discover_mcp_tools` + `registry.get_entry("mcp__arthub__…").handler({…})`) from the hermes-agent checkout — same payloads as native tools. See `references/arthub-mcp-contract.md`.
- **H1-less bodies are rejected (`h1-count` ERROR).** Every md artifact must carry exactly one `# ` heading — the server rejects a document with zero H1s, so a multi-part split cannot publish "part 2" as a bare `## …` continuation. Give each part its own H1 before publishing, keep the pre-split local body as the canonical source, and cross-link part N+1 back to part N's raw URL.
- **Stream timeout on large tool-call arguments in interactive sessions (~8K tokens).** A single `write_file` (or any tool call) carrying more than roughly 8K tokens of content can time out the stream before delivery; the runtime rejects it and asks for smaller calls. For long article bodies, write 3–4 chunk files (~4–6KB each) with separate `write_file` calls, then concatenate with `cat p1.md p2.md p3.md > final.md`. This pairs with the in-process publish handler (body read from disk), so no large inline argument exists anywhere in the pipeline. Observed 2026-08-09 with a ~20KB Korean article: chunked write + `cat` + in-process publish worked end to end.
- **`tool_call` argument size limit (~32KB) truncates silently in cron mode.** When publishing a 30–40KB body via deferred `tool_call mcp__arthub__publish_artifact` or `update_artifact`, the JSON argument appears to ship fine but the server receives a truncated body. The artifact is created with a body cut mid-line (e.g. mid-LMCache in a 37KB daily report) and you do NOT get an error. Detection: `read_artifact` immediately after a large publish shows a body ending mid-PR-description. **Switch to the in-process handler BEFORE the second publish**, not after the first truncated one. The cron-safe pattern is `terminal python3 <<'PY' ... PY` with `discover_mcp_tools()` + `registry.get_entry("mcp__arthub__update_artifact").handler({"slug":..., "content":open("/tmp/body.md").read(), ...})` — file-read sidesteps the argument-size cap entirely. Observed 2026-08-07: 37KB body → v2 created with ~32KB (truncated mid-LMCache section) via `tool_call`; v3 same problem; v4 finally complete after switching to the in-process handler with the body read from `/tmp/full_body.md`. Truncated v1/v2/v3 are NOT recoverable — they remain in version history. **Heuristic**: any body > 30KB → write to a file and use the in-process handler from the start. Bodies < 30KB are safe in `tool_call`. Alternative for a ~30-40KB interactive body: split at a top-level `## ` boundary into 2–3 standalone artifacts — each part ≤ ~16KB ships fine through deferred `tool_call` (discover with `tool_search`/`tool_describe` first) — reusing project/tags/visibility and giving every part its own H1 (see the `h1-count` pitfall); compare each `read_artifact` read-back against its corresponding split file, and cross-link the parts.
- **Truncated-v1 stamp on a long body is a near-certainty for cron agents.** A first publish via `tool_call` with a 35–45KB body almost always lands a v1 with the body cut at the tool-side argument limit (~32KB). The mistake is treating `Created v1` as success and moving on. **Always do an immediate `read_artifact({id})` read-back after the first publish and compare body length to the local source file** — if the returned body is shorter mid-line, switch to the in-process handler for the next version. Don't keep retrying via `tool_call`; the cap is per-call.
- **YouTube talk + paper Artifact notes.** Default path is `youtube-full-transcript-localization`: spoken-language captions first (Korean talk → `ko`, not EN→KO), **refine** into readable notes (not ASR dump), crop report figures (not full pages), place inline, in-process publish when body is large. Bundled `youtube-content` is fetch-only and not curator-editable.
- **Section warnings ignored:** Artifact Hub may report `empty-section` when a level-2 heading is followed immediately by a level-3 heading even if the subsection has content. Also fires when a heading is followed only by a table/list with no prose — add one natural intro sentence before the table. Republish until structural warnings are gone. Treat other linter warnings similarly: remove accidental key-value list patterns or rewrite them deliberately, then publish a clean version.
- **`empty-section` on transcript H2 + timestamp H3.** Shape `## 5. KDA` then immediately `### [12:30]` always trips the linter. **One natural Korean intro sentence under every H2** before the first `###` or table.
- **`prefer-table` on numbered TOC and formula callouts.** A 12-item markdown TOC and blockquotes like `α_t: channel-wise ...` read as key:value runs. Prefer a two-column TOC table, put formulas in a fenced `text` block, rewrite speaker meta lines as plain sentences or a meta table. Residual single `prefer-table` after two clean passes is acceptable — do not wreck readability chasing zero.
- **`publish_artifact` `tags` behavior differs by invocation path.** The deferred MCP boundary has rejected a flat JSON string array with `Items did not match schema; Items/0: Instance type "object" is invalid. Expected "string".` even though the declared schema expects strings. Do not blindly omit tags: when the body is large or the boundary rejects the payload, use the in-process registry handler (`discover_mcp_tools()` + `registry.get_entry('mcp__arthub__publish_artifact').handler(...)`) with the same `(project, slug)` and explicit tags, then verify tags via `list_artifacts`/canonical read-back. If the in-process path also rejects tags, accept/report empty tags rather than inventing a coercion. Keep the live contract note in `references/arthub-mcp-contract.md` current.
- **`prefer-table` false positive on focus / category lines.** The linter reads any `_포커스: Label: a, b, c` line (colon inside the focus text followed by 3+ comma-separated items) as a list of `key: value` bullets and reports `prefer-table`. Triggered lines observed: `_포커스: JIT attention kernels, CuTeDSL, MoE EP, FP8 fused_`, `_포커스: TIS: 다중 모델 backend, dynamic batching, ensemble, BLS_`. Two fixes that work: (1) drop the inner colon — `_포커스 — TIS 다중 모델 backend, dynamic batching, ensemble, BLS_`; (2) move the marker off the same line and put the list on a new line. Either is a 1-line edit per focus line. Iterate one fix per publish, not all at once — a partial fix sometimes surfaces a *new* warning that was masked by a different pattern.
- **`prefer-table` false positive on an actual Markdown table.** A separate failure mode from the focus-line and label-token cases above. When a 3+ row Markdown pipe table sits at the start of the body (right under the H1 + blank line), the linter reads each `| col | col |` row plus the trailing paragraph as four `key: value` bullets in a row and reports `prefer-table`. Observed 2026-08-07 on the W31 industry weekly: an explicit `| Primitive | 의미 |` 3-row table after a `# 🏢` H1 still produced `Warning prefer-table: 4 key: value bullets in a row` on the response from `update_artifact`. **The linter does not parse Markdown pipe tables as tables.** Workarounds: (1) collapse the table to 2 rows; (2) drop the `|` separators and use a list (the focus-line pattern above); (3) move the table to a later position in the body, away from the H1, so the linter's windowed scan no longer sees it. Do not chase this warning past two publish iterations — it is a known linter limitation, not a content defect, and rephrasing a real table to please the linter hurts the reader.
- **`empty-section` on a clean H1 + intro line + H2 layout.** The existing pitfall above covers H2→H3 nesting and tables/lists directly under a heading. A separate trigger fires when the very top of the document is `# H1\n\nintro paragraph\n\n## H2` and the linter reports `empty-section` on the H1 line because it sees no body before the H2 — the intro paragraph is treated as belonging to a different section. Observed 2026-08-07 on the same W31 weekly: `Warning empty-section: This section has a heading but no body.` fired on line 1 of the H1 even though a full intro paragraph was two lines below. Workarounds: (1) drop the H1 entirely and let the document start with the H2 (acceptable when the detail page already shows the title); (2) merge the intro into the H1 line as a subtitle paragraph separated by `—`; (3) accept the warning as a known false positive and move on. Again, do not chase past two iterations.
- **`update_artifact` may rewrite the `title` field server-side.** When `publish_artifact` and `update_artifact` are called with an explicit `title`, the server may normalize it on the way in: an H1 emoji + short title in v1 was stored as `LLM Serving Industry Weekly — 2026-W31`, and the same call's v2 response showed `🏢 LLM Serving Industry Weekly — 2026-W31 (07-27 ~ 08-02)` — the emoji and the date range from the H1 line were folded into the stored title. Title is not a guaranteed-input field; the server appears to derive it from the first H1 of the body when the explicit title is short, and from the explicit title when it is long. Implication: do not rely on `read_artifact.title` byte-equaling the `title` you sent. If the user-facing title in the index must be exact, encode it in the H1 of the body rather than in the `title` parameter, and treat `read_artifact.title` as informational. Confirmed variant: `update_artifact` (which accepts no title parameter) re-derives the stored title from the body H1, discarding the title the original `publish_artifact` call had stored — the H1 is the title authority across versions, so encode the user-facing title in the H1 from v1 on.
- **`html render` blocks make the raw endpoint a ~2KB shell.** When the md body contains ```html render fences, `artifact-content.sharosoo.com/raw/<id>` returns about 2KB with only the title and the live-block iframe. The block bodies load client-side from `/resource/<id>/block/<hash>` in a cross-origin iframe. grep-for-phrase checks on raw HTTP will fail even when the article is correct. Verify with a browser: open the raw URL, confirm the H1 and one `iframe[src*="/block/"]` exist, and check the iframe's rendered height (observed 6709px for a long block). The detail page shows only metadata. Observed 2026-10-08 on the OSC 7501 review (v1).
- **Raw endpoint returns an HTML wrapper, not the source Markdown.** `https://artifact-content.sharosoo.com/raw/<id>` serves a fully rendered HTML page (with `<!doctype html>`, `<title>`, and the Markdown converted to semantic HTML), not the Markdown source you sent. A 5.9KB Markdown body produces ~9.1KB of HTML. The `truncated-v1` heuristic (compare `len(read["content"])` to the source) applies only to the canonical MCP `read_artifact` response, never to the raw HTTP endpoint. Verification via raw should use `curl -sS -o /tmp/check.html -w 'HTTP %{http_code}, bytes %{size_download}\n'` followed by `grep` for distinctive phrases from the body — never byte-equality against the source file. **Keep verification manifests limited to durable files**: do not assert that a transient `/tmp` helper still exists after an earlier verification run deleted it. Compile persistent helpers or the canonical report-generation scripts, and test transient-probe creation/deletion independently in the same run.
- **`prefer-table` from colon-bearing label tokens (`op: moe`, `op: attention`, `op: gemm`).** Distinct from the focus-line trigger above. The depth-mode daily report emits consecutive per-PR label bullets like `- 🏷 \`run-ci, op: moe\``, `- 🏷 \`run-ci, op: moe, op: attention\``, `- 🏷 \`run-ci, op: moe\``. When 3+ of these appear in a row the linter reads `op: moe` as a `key: value` bullet and reports `prefer-table`. The generic per-PR bullet pattern (`🏷 label1, label2, label3`) without colons is benign — only the **colon inside a label token** triggers it. Fix: replace `:` with `-` in label tokens before publish — `op: moe` → `op-moe`, `op: attention` → `op-attention`, `op: gemm` → `op-gemm`. Observed 2026-08-07: 3 consecutive FlashInfer `op: moe` lines triggered the warning; rewriting tokens to `op-moe` cleared it in one publish. Same root cause for the SGLang / vLLM / TRT-LLM label families when they accumulate 3+ colon-bearing tokens in adjacent bullets.
- **`prefer-table` from consecutive `- **label**: text` bullets.** 3+ markdown bullets shaped `- **display_idx 비동기 갱신**: 설명...` (bold label immediately followed by a colon) trip the linter as key:value runs — the bold-colon styling variant of the label-token case above. Fix: swap the colon for an em dash — `- **label** — 설명...` — and the warning clears in one publish. The same trigger also fires for blockquote bullets `> - **label**:` and the paren variant `- **label** (paren):`; one regex covers all three — `re.sub(r'(?m)^(\s*(?:>\s*)?-\s*)\*\*([^*]+?)\*\*((?:\s*\([^)]*\))?)\s*:\s*', r'\1**\2**\3 — ', s)`. Observed 2026-08-09 on a long-form article: section bullets (`- **display_idx(채팅방 정렬 키) 비동기 갱신**: ...`) and `- **GIL**: ...` style lists both triggered it. A `###` heading containing a colon (`### 6.2 Discord: ...`) was flagged in the same pass; replacing the heading colon with an em dash is a cheap hedge when the warning line points at a heading. Plain (non-bold) bullets with an early colon (`- 배경: ...`) trip the same detector in a 3+ run; where the em-dash swap would read unnaturally, rewrite the label as a topic sentence instead (`배경은 ...이다`).
- **`prefer-table` from a colon in an H2 heading (not only `###`).** Observed 2026-08-10: `## Prompt · Tool · Skill: 에이전트를 구성하는 세 층` produced `Warning prefer-table: 4 key: value bullets in a row` whose line number pointed at the heading, even though the section contained an ordinary pipe table + paragraph. Fixing just that one colon (→ em dash) moved the warning to the NEXT colon heading (`## Progressive disclosure: ...`). Batch-replace ALL colon-bearing H2 headings in one pass (`sed -i 's/^## \(.*\): /## \1 — /' body.md`), then republish — 0 warnings in a single update. Same root cause appearing N times is one fix applied N times, not N separate iteration units (the one-fix-per-publish rule targets *different* warning sources).
- **Iteration loop for cleaning linter warnings.** Publish → read `warnings[]` from the response → fix one source of warnings per patch → `update_artifact` with `base_version` → repeat. Observed: v1 had 2 warnings (focus lines on Triton-Inference-Server and FlashInfer), v2 fixed one and dropped to 1, v3 fixed the other and reached 0. Do NOT batch all fixes into a single patch. After every publish, re-read the response's `warnings[]` and treat each one as its own iteration unit. The `prefer-table` warning is non-blocking for publish (it is a `WARN`, not `ERROR`), but a clean revision with no warnings is the verification target.
- **Test publish leaves an artifact on the server.** When validating the live `publish_artifact` contract (e.g. to confirm whether `tags` is broken), use a small minimal body with a `-test` suffix in the slug and title. The configured MCP surface does not always expose `delete_artifact` or `move_artifact`, so a test artifact may stay live indefinitely. Per `canonical-slug-and-duplicate-recovery.md`, make the test document unmistakably internal: short body, no public value, and add `internal,test,duplicate` tags if tags work. Do not delete-by-republishing the canonical artifact with a test body — that loses the canonical version. If a previous session's test artifact exists, do not silently delete it; the live surface may not support deletion, and the user may have indexed it.
- **Wrong slug on revision:** using a new slug while holding the old Artifact ID creates a separate `v1`; identity is `(project, slug)`. If the service has no delete/archive tool, keep the original canonical, make the accidental duplicate private with an unmistakable internal duplicate body, verify its public detail URL is inaccessible, and omit it from all indexes and manifests.
- **Wrong origin diagnosis:** testing a content resource path against the detail-page origin. Verify live blocks from the rendered content origin.
- **Images are absent from extracted article text.** `web_extract` returns prose only — no `<img>` tags, no `[IMAGE: …]` placeholders — so a translation built from it silently loses every figure. Harvest images from the rendered DOM in one `js()` pass per URL: walk `h1,h2,h3,h4,p,figure,img,ul,ol,table,pre` in document order tracking the last heading, emit `img.currentSrc || img.src` plus the caption from `closest('figure')`'s `figcaption`/`p`, filter to the site's asset path, skip hero/banner art, and **dedupe by `src`** — a nested selector list returns the same image twice (once as `img`, once via its parent), otherwise doubling every caption. Never construct an asset URL from the article slug: asset folders are dated independently of the post URL and shared across posts. Figures reporting `naturalWidth === 0` are lazy-loaded below the fold, not broken; verify reachability with a ranged `curl`.
- **Vendor news pages may carry zero `<img>` figures — charts exist only as DOM/SVG.** The figure-harvest pass then finds nothing, and a translation publishes without the figures the user asked to preserve. Extract values from `aria-label` attributes (scatter points), CSS-grid divs flattened in document order (not `<table>`), and inline `<svg>` text nodes; rebuild the charts as dual-theme SVGs and rasterize with headless Chrome — recipe: `references/external-article-ko-translation.md` → DOM/SVG chart replication.
- **AI-rendered diagram text:** image generation models mangle text and Korean comes out as garbage — generate art-only assets (prompt "no text, no letters") and overlay labels with PIL. Draft label text in English and naturalize it with the local `agy` CLI (`agy --print <prompt> --dangerously-skip-permissions`, JSON out) before rendering; never hand-write Korean labels into figures. Use ASCII `-` for negatives (Nanum fonts render U+2212 as tofu), measure label width against the slot before committing, and upload a changed image under a new key (`fig-v2.png`): CDN objects are cached immutable for a year and `sharosoo-cdn put` refuses in-place overwrites. Full recipe: `references/ai-diagram-and-photo-annotation.md`.
- **Linter errors discovered at publish time.** Run `scripts/preflight_ko_markdown.py <body.md>` on every locally composed body before the first publish — it catches raw HTML, unpaired `**`, colon headings, `- **label**:` bullets, the missing-blank-line traps, H2-without-intro, uncaptioned images, task-list inline code, forbidden phrasing, and unbalanced fences in one pass. Fixing them per publish response costs one artifact version per warning source. Write image captions as `_..._` on the line right after the image — the checker requires the caption line to start with `_`, so `*...*` captions trip the image-caption warning and cost a re-lint pass.
